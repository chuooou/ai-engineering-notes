# DTO 변경 대응 업무를 AX 관점에서 재설계해보기

## 0. 왜 이 글을 쓰는가

프론트엔드 개발을 하다 보면 Backend API의 DTO가 변경될 때마다 Swagger를 확인하고(간혹 친절하게 바뀐 부분이 뭔지 알려주시는 백엔드분들에게 무한감사), 해당 API와 Type을 사용하는 코드를 찾아 수정한 뒤 다시 테스트하는 작업을 반복하게 된다.

작업 자체는 전혀 어렵지 않지만, 변경이 잦아질수록 탐색과 수정 작업을 계속 반복해야 하고 사용 및 관련 코드를 하나라도 놓치면 화면 오류나 예상하지 못한 버그로 이어질 수 있다.

최근 AX(AI Transformation)를 공부하면서 단순히 AI를 사용하는 것보다 **기존 업무 프로세스에서 어떤 단계는 자동화하고, 어떤 단계에는 AI를 사용하며, 어떤 판단은 사람이 해야 하는지를 나누는 것**이 중요하다는 것을 알게 되었다.

그래서 평소 반복적으로 불편함을 느꼈던 **DTO 변경 대응 업무를 AX 관점에서 다시 설계해보기로 했다.**

---

## 1. 현재 문제

Backend에서 DTO가 변경되면 Frontend에서는 일반적으로 다음 작업이 필요하다.

1. Backend 개발자로부터 DTO 변경 완료 내용을 전달받는다.
2. Swagger/OpenAPI에서 변경된 DTO를 확인한다.
3. 해당 DTO 또는 API를 사용하는 코드를 검색한다.
4. Type과 DTO 사용 코드를 수정한다.
5. 영향받는 Component나 Business Logic을 확인한다.
6. Type Check 및 API 테스트를 진행한다.
7. 문제가 없다면 변경사항을 Commit한다.

하나의 DTO가 변경되는 것은 작은 작업처럼 보이지만, 실제로는 여러 파일과 화면에서 동일한 Type을 사용할 수 있기 때문에 **변경 영향 범위를 사람이 직접 추적해야 한다.**

특히 다음과 같은 문제가 있다.

* DTO 변경 빈도가 높아 반복 작업이 자주 발생한다.
* 사용처 탐색과 영향 범위 확인에 시간이 소요된다.
* 코드 하나라도 수정하지 못하면 에러 및 런타임 문제로 이어질 수 있다.
* 작업 자체보다 변경된 부분을 찾고 확인하는 데 반복적인 시간이 사용된다.
* 사람이 직접 사용처를 추적하기 때문에 누락과 같은 Human Error 가능성이 존재한다.

현재 체감 기준으로 이 업무를 평가하면 다음과 같다.

| 항목         |      점수 |
| ---------- | ------: |
| 발생 빈도      |   5 / 5 |
| 소요 시간      |   3 / 5 |
| 실수 가능성     |   2 / 5 |
| 오류 발생 시 피해 | 2~3 / 5 |

아직 정확한 개선 효과를 측정한 것은 아니기 때문에 임의의 시간을 작성하지 않았다.

향후 실제 구현 단계에서는 DTO 변경 사례를 기준으로 다음 값을 직접 측정해볼 예정이다.

* DTO 하나 변경 시 기존 대응 시간
* 영향받는 파일 개수
* 사람이 직접 검색하는 데 걸리는 시간
* 자동 탐지한 사용처 중 실제 영향받는 코드의 비율
* AI가 제안한 수정 중 사람이 다시 수정한 비율

이 값을 기준으로 AX 적용 전후를 비교해볼 수 있다.

## 2. Before Workflow

현재 업무 흐름을 단순화하면 다음과 같다.

```text
DTO 변경 이슈 발생
      ↓
Backend DTO 수정
      ↓
변경 완료 전달
      ↓
Frontend 개발자가 Swagger 확인
      ↓
DTO/API 사용처 검색
      ↓
Type 및 관련 코드 수정
      ↓
Type Check / API Test
      ↓
최종 확인
      ↓
Commit
```

이 과정에서 가장 반복적인 부분은 **변경사항 파악 → 영향 코드 탐색 → 코드 수정 → 검증**이다.

---

## 3. 각 단계를 Rule / AI / Human으로 나누기

처음에는 반복되는 작업이기 때문에 전체 과정을 AI에게 맡기면 되지 않을까 생각했다.

하지만 각 단계를 나눠보니 모든 작업에 AI가 필요한 것은 아니었다.

### Rule

#### OpenAPI 변경 감지

이전 Schema와 새로운 Schema가 다른지는 명확하게 비교할 수 있다.

AI가 변경 여부를 추론할 필요 없이 프로그램으로 비교하는 편이 더 정확하고 빠르다.

#### Schema Diff 생성

예를 들어 다음과 같은 변경은 기계적으로 판단할 수 있다.

```text
name → displayName
string → number
required → optional
field 추가 / 삭제
```

따라서 AI보다 Rule 기반 처리가 적절하다.

#### Reference 검색

특정 DTO가 어느 파일에서 import되고 있는지, 특정 API를 어디에서 호출하고 있는지는 AST, TypeScript Language Server의 Find All References 또는 일반적인 문자열 검색(Ctrl+Shift+F)을 이용해 찾을 수 있다.

단순한 위치 탐색에는 AI의 추론 능력이 필요하지 않다.

#### Type Check / Lint / Test

테스트 실행 자체는 결과가 명확하다.

```text
PASS
FAIL
```

따라서 이 과정도 AI보다 기존 자동화 도구가 담당하는 것이 적절하다.

---

### AI

#### 변경 영향 분석

코드의 위치를 찾는 것과 그 코드가 **DTO 변경으로 실제 어떤 영향을 받는지 판단하는 것**은 다른 문제다.

예를 들어

```ts
status: "ACTIVE" | "INACTIVE"
```

였던 값이

```ts
status: "ACTIVE" | "INACTIVE" | "PENDING"
```

으로 변경되었다면 TypeScript Error가 발생하지 않더라도 기존 Business Logic이 잘못 동작할 가능성이 있다.

이처럼 코드 문맥을 이해하고 변경 의미를 분석해야 하는 작업에는 AI를 활용할 수 있다.

#### 수정 계획 생성

변경된 Schema와 영향받는 코드를 기반으로

* 어떤 Type을 변경해야 하는지
* 어떤 Component가 영향을 받는지
* 어떤 조건문을 다시 확인해야 하는지

등의 수정 계획을 AI가 먼저 생성할 수 있다.

#### 코드 수정안 생성

수정 대상과 변경 목적이 정리된 상태라면 AI가 실제 코드 수정안을 제안할 수 있다.

#### 테스트 실패 원인 분석

테스트 실행 자체는 Rule이 담당하지만, 실패한 Error Message와 관련 Code Context를 읽고 가능한 원인을 분석하는 것은 AI가 활용될 수 있는 영역이다.

---

### Human

#### DTO 변경 의도 및 Business Logic 판단

DTO가 왜 변경되었는지, 새 값이 실제 서비스에서 어떤 의미를 갖는지는 단순한 Schema 정보만으로 판단할 수 없는 경우가 있다.

따라서 중요한 Business Logic은 개발자가 최종적으로 판단해야 한다.

#### 최종 Diff Review

AI가 코드 수정안을 만들었다고 하더라도 불필요한 변경이 포함됐거나 서비스 의도와 다른 수정이 있을 가능성이 있다.

따라서 최종 변경사항은 사람이 확인한다.

#### 최종 승인

자동 테스트를 통과했다고 해서 Business Logic까지 항상 올바르다고 보장할 수 없으므로 Merge와 같은 최종 결정은 사람이 담당한다.

## 4. After Workflow

이를 기반으로 다음과 같은 Workflow를 생각해볼 수 있다.

```text
OpenAPI 변경
      ↓
[Rule]
변경 감지
      ↓
[Rule]
Old / New Schema Diff 생성
      ↓
[Rule]
관련 API / DTO Reference 검색
      ↓
[AI]
변경 영향 범위 분석
      ↓
[AI]
수정 계획 생성
      ↓
[AI]
코드 수정안 생성
      ↓
[Rule]
Type Check / Lint / Test
      ↓

    실패 ───────── 성공
      ↓              ↓
    [AI]          [Human]
실패 원인 분석     Diff Review
      ↓              ↓
수정안 재생성     Business Logic 확인
                     ↓
                  PR / Merge
```

여기서 중요한 것은 **AI가 모든 과정을 처리하도록 만드는 것이 목표가 아니라는 점**이다.

정확한 결과를 프로그램으로 얻을 수 있는 작업은 기존 자동화를 사용하고, 문맥과 추론이 필요한 작업에 AI를 사용하며, 책임 있는 판단은 사람이 담당하도록 구성했다.

---

## 5. 기대 효과와 평가 방법

현재 단계에서는 아직 설계만 진행했기 때문에 실제 생산성 향상을 주장할 수는 없다.

대신 구현 후 다음 항목을 기준으로 AX 적용 효과를 확인해볼 수 있다.

### 시간

```text
DTO 변경 대응 평균 시간
Before → ??분
After  → ??분
```

### 영향 범위 탐지

```text
실제 영향 파일: N개
자동 탐지 파일: N개
누락: N개
```

### AI 수정 품질

```text
AI가 수정한 코드 중
그대로 사용: %
개발자가 일부 수정: %
완전히 다시 작성: %
```

### Human Error

DTO 변경 후 발견된 누락 사용처나 잘못된 수정 건수가 감소하는지도 확인할 수 있다.

단순히 "AI를 사용했다"가 아니라 **실제로 시간과 오류가 얼마나 감소했는지 측정하는 것이 AX의 최종 목표**라고 생각한다.

## 6. 이번 설계를 하면서 배운 점

처음에는 반복되는 개발 업무라면 AI Agent가 전체 과정을 수행하도록 만드는 것이 AX라고 생각했다.

하지만 Workflow를 단계별로 나눠보면서 AI를 많이 사용하는 것이 좋은 AX 설계는 아니라는 점을 알게 되었다.

Schema 비교, Reference 검색, Test 실행처럼 결과를 명확하게 판단할 수 있는 작업은 기존 프로그램이나 Rule 기반 자동화가 AI보다 빠르고 예측 가능하다.

반대로 변경된 DTO가 실제 Business Logic에 어떤 영향을 주는지 판단하거나 여러 코드의 문맥을 함께 분석해야 하는 작업에서는 AI의 장점을 활용할 수 있다.

결국 이번 설계를 통해 다음 기준을 세울 수 있었다.

결과를 규칙으로 확정할 수 있다
→ Rule

문맥을 이해하고 추론해야 한다
→ AI

서비스 의미와 책임 있는 판단이 필요하다
→ Human

그리고 AX의 핵심은 단순히 업무에 LLM을 붙이는 것이 아니라 기존 Workflow를 분석하고 Rule, AI, Human의 역할을 다시 설계하는 것​이라는 점을 이해하게 되었다.

이번 과정을 거치면서 어떤 업무가 AX 후보가 될 수 있는지를 보는 감각도 조금 생긴 것 같다.

예전에는 반복적인 업무를 보면 단순히 "AI로 자동화할 수 있을까?"부터 생각했다면, 이제는 먼저 다음과 같은 질문을 생각하게 되었다.

이 작업은 반복적인가?

입력과 결과를 명확하게 정의할 수 있는가?

Rule만으로 해결할 수 있는 부분은 어디인가?

문맥이나 추론이 필요한 부분은 어디인가?

AI가 틀렸을 때 피해는 어느 정도인가?

어느 단계에서 사람이 확인해야 하는가?

즉, AX 아이디어를 찾을 때도 단순히 "AI를 어디에 넣을까?"​를 생각하는 것이 아니라, 기존 업무 흐름을 먼저 분석한 뒤 AI가 실제로 가치를 만들 수 있는 지점을 찾는 방식으로 접근해야 한다는 감각을 조금씩 익히고 있다.

다음 단계에서는 이 Workflow 중 가장 작은 부분부터 실제로 구현해보려고 한다.

우선 OpenAPI의 Old/New Schema를 비교해 변경사항을 추출하고, 해당 DTO의 Frontend 사용처를 자동으로 찾는 과정부터 구현한 뒤 AI 기반 영향 분석을 추가해볼 예정이다.
